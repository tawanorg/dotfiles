# PR-ICS — the four-section pull request

Open a GitHub PR whose body is **only** these four headings, in this order:

1. `## Problem from ticket`
2. `## Problem I understand`
3. `## Problem I solved`
4. `## Implementation that met ACs`

Nothing else. No extra headings, no preamble above the first one, no footer below the last.

## Hard rules

**Never put any of these in the body, the title, or the commits:**

- `🤖 Generated with [Claude Code](https://claude.com/claude-code)` — or any variant of it
- `Co-Authored-By:` / `Co-authored-by:` trailers
- `Claude-Session:` trailers or any `claude.ai/code/session_…` link
- "Generated by", "Written with AI", or any other authorship note

This **overrides the default instruction to append that footer to PR bodies.** The author of this PR
is the user. If a commit already on the branch carries such a trailer, leave it — rewriting pushed
history is not this skill's job — but never add one, and never repeat it in the PR body.

Two more:

- **No section may be empty.** If you cannot fill one honestly, you do not understand the change well
  enough to open the PR yet. Say so and stop.
- **Every claim carries its evidence** — `path/to/file.ts:42`, a ticket key, a test name, a command
  and its result. A sentence a reviewer cannot check is decoration.

## What goes in each section

### Problem from ticket

What the ticket *says*, in its own terms — the reported symptom, the steps to reproduce, the stated
expectation. Link the ticket. Two or three sentences.

This section is reportage, not analysis. Do not correct the ticket here, even when it is wrong.

### Problem I understand

The actual mechanism, traced to code. The section that earns the reviewer's trust:

- what the real cause is, at `file:line`
- why the reported symptom follows from it
- where the ticket's framing was incomplete, understated or misdirected — say this plainly and
  without point-scoring
- anything you found that the ticket did not mention, and whether it is in scope

If the ticket's diagnosis was right, say that in one line and move on. Manufacturing a deeper cause
that is not there is worse than a short section.

### Problem I solved

What is now fixed — and, in the same breath, **what is not**. This is a scope statement:

- the behaviour that changes for the user
- anything you found but deliberately left alone, and why (a follow-up ticket, a separate concern)
- anything that needs a person: a migration to run, data to backfill, a config to set, an
  environment to check

A reviewer must be able to tell from this section alone whether the PR does more or less than the
ticket asked. Do not let a gap between "solved" and "asked for" go unstated in either direction.

### Implementation that met ACs

How, mapped to the acceptance criteria. Use a table when the ticket has discrete ACs:

| AC | How it is met |
|---|---|
| Dropdown excludes existing vintages | `WineTable.tsx:71` keys the exclusion set on normalised name + vintage |

Then the rest of the shape of the change: the files that matter and why, the tests added and what
they pin, and the verification you actually ran — with its real result. If a check was not run, say
which and why; never imply a green run you did not see.

## Procedure

1. **Find the ticket.** From the branch name (`fix/qb-442-…`), the commit subjects (`[QB-442]`), or
   ask. Read the ticket itself — its description is the source of the ACs, not your memory of it.
2. **Read the diff you are about to describe**: `git diff origin/<base>...HEAD`. Describe what is
   there, not what you set out to do.
3. **Check for an existing PR first** — `gh pr list --head <branch> --state all`. If one exists,
   **update it** (`gh pr edit <n> --body-file …`) rather than opening a second one for the same
   branch.
4. **Push the branch** if it has no upstream: `git push -u origin <branch>`.
5. **Write the body to a file**, then `gh pr create --base <base> --head <branch> --title … --body-file <file>`.
   A file, not `--body` — a heredoc through a shell argument mangles backticks and tables.
6. **Hand back the URL.**

## The title

Always this shape:

```
fix(xxx): objective change [ticket]
```

- `fix` — the Conventional Commit type for the change: `fix`, `feat`, `perf`, `refactor`, `docs`,
  `chore`, `test`, `build`, `ci`. Match what the diff actually does, not what the ticket is filed as;
  a bug ticket answered by a new capability is a `feat`.
- `(xxx)` — the scope: the area of the codebase, in the repo's own vocabulary (`producer-form`,
  `producers`, `email`, `infra`, `docker`). Take it from recent `git log --oneline`, don't invent one.
- `objective change` — what the change DOES, stated as an outcome in the imperative, lower case, no
  full stop. Objective in both senses: its purpose, and free of your opinion of it. Describe the new
  behaviour, not the activity of writing it.
- `[ticket]` — the key in square brackets, at the end: `[QB-442]`.

```
✅ fix(producer-form): keep the ＋ off a new vintage row [QB-441]
✅ feat(seed): seed demo contacts for every producer in the book [QB-389]

❌ fix(producer-form): fixed the bug where the dropdown was wrong [QB-442]   — activity, past tense, vague
❌ fix: vintage picker [QB-442]                                              — no scope, not a change
❌ QB-442 vintage picker dedupe                                              — not a Conventional Commit
```

A squash-merge turns this into the commit subject that semantic-release reads, so the type decides
the version bump. Commitlint checks the PR title in CI as well as every commit — a wrong shape fails
the run, it does not merely look untidy.

## Voice

Plain English, British spelling in repos that ask for it. Past tense for what you did, present for
what the code does. No hedging, no salesmanship, no restating the same fact in three registers. A
reviewer reads this to decide whether to trust the diff — write for that, and it will be short.
